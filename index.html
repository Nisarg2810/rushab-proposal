03

The website, page by page

Every page has one job. Nothing on the site exists because other travel sites have it.

  • Home. One search box tuned for packages, the packages people actually booked this month, your destinations, and the four reasons someone books with a planner instead of an app.
  • Destination pages. Andaman, Kerala, Kashmir, Dubai and the rest each get a real page with their own packages, their own photos and their own text. This is what brings search traffic.
  • Package listing. Filters for destination, trip length, budget, theme and departure city, with sorting by price or by length. Fast, with no page reloads.
  • Package page. Gallery, day by day itinerary, the named hotels with star rating, room type and meal plan, the sightseeing list, what is included, what is not, cancellation and payment policy, and a price box that follows you down the page.
  • Enquiry. Short form, three fields that matter, and a confirmation that tells the traveller exactly when they will hear back.
  • Flights and hotels. A clean strip that hands the traveller to your booking partner, without pulling them away from packages.
  • Group departures, visa, about, contact. Simple pages, all editable by your team.
Built in from day one

Fast on a cheap phone

Pages are rendered on the server and images are resized and served in modern formats. The target is a package page that opens in under two seconds on 4G.

Found on Google

Search ready, not search bolted on

Clean URLs like /holidays/andaman/3-nights-4-days, editable titles and descriptions per package, structured data for prices and reviews, a sitemap that updates itself.

Every screen

Designed on the phone first

Most of your traffic is mobile. The filters, the gallery and the price box are built for a thumb, then widened for a laptop.

The dashboard, so you never wait on a developer

Everything a traveller reads on the site is a field your team can edit at dashboard.rushabtours.com. No code, no tickets, no agency in the middle.

Packages

Eight tabs, one package

Overview, hotels, itinerary, sightseeing, inclusions, pricing, gallery and the Google listing. Drag a day to reorder it, duplicate last year's package to build this year's.

Photos

A media library, not a folder

Upload once, use the same photo across packages and destinations. Resizing, cropping and compression happen for you.

Pricing

Rates by date range

Regular and peak rates, child with bed and without, and a strike through price. The site always shows the rate for the date the traveller picked.

Destinations

Each one is a page

Hero photo, description, best months and the packages attached to it. Add a new destination without touching the code.

Control

Draft, preview, publish

Work on a package privately, preview it exactly as a traveller will see it, publish when it is ready. Mistakes are one click back.

People

Roles that make sense

Owner sees everything. A manager edits packages and works leads. Sales sees only leads. Content sees only packages and photos.

07

WhatsApp, scripted first and then a real person

The bubble at the bottom right does not just open WhatsApp. It asks three or four questions first, so your team opens the chat already knowing what the trip is.

Step oneOn the site

A short scripted chat

Where would you like to go, when, how many travellers, and your budget. Buttons, not typing. It takes fifteen seconds and feels like a conversation rather than a form.

Step twoHandover

It moves to real WhatsApp

The traveller taps once and lands in a WhatsApp chat with your number, with their answers already written into the first message. Nobody has to repeat themselves.

Step threeIn the dashboard

It is already a lead

Before your team even replies, the chat has created a lead with the answers, the source and the page they were on. Chats stop getting lost in a phone.

LaterOptional

Official WhatsApp Business API

If you want quote PDFs, payment reminders and itinerary updates sent automatically, we can connect the official API. It carries a small per message cost from Meta, so we would only do it once the enquiry volume justifies it.

08

How it is built

Exactly the stack you specified. All of it is mainstream and well documented, so you are never locked to one developer, including us.

FrontendNext.js, React, TypeScriptServer rendered pages for speed and for Google, typed code so a change in one place cannot quietly break another.
StylingBootstrap, responsiveA familiar grid any developer can pick up, with a Rushab Tours theme layered on top so it does not look like a template.
BackendNode.js, NestJS, RESTA clean REST API with validation, roles and documentation, so the site, the dashboard and anything you add later all talk to the same thing.
DatabasePostgreSQLPackages, itineraries, prices, leads and users, with daily automated backups and point in time recovery.

Hosting and deployment

Frontend on a global edge network, API and database on a managed host in the India region so pages load fast for Indian travellers. Deployments are automated, and any release can be rolled back.

Security

HTTPS everywhere, hashed passwords, role based access, rate limited forms, spam protection on the enquiry form, and an audit trail of who changed which package.

Yours, not ours

The code sits in a repository in your name, the domains and hosting stay in your accounts, and the database can be exported any time. Handover is written into the plan, not promised at the end.
